# Model Card — Abuse-Ring Sentinel Detection System

**Status:** Current snapshot. Historical Checkpoint 0 specification text is retained
below; see [STATUS.md](STATUS.md) for authoritative implementation state.
**Owner:** ML + Evaluation Agents (see `AGENTS.md`)
**Last updated:** 2026-08-24

This card follows the spirit of a model card but describes a *detection system*
composed of several models and signal engines rather than a single model. It will
be updated with measured results as checkpoints complete.

> **Scope.** This is a research/portfolio fraud intelligence system trained and
> evaluated entirely on synthetic data. It is not validated for, certified for, or
> suitable for real financial decisioning. Nothing in this card describes
> real-world performance.

---

## 1. System overview

Abuse-Ring Sentinel scores transactions for fraud risk by combining four
independently computed signals — transaction, temporal, graph, and reputation —
into a single 0–100 risk score with an attached, human-readable explanation. The
constituent models are:

| Component | Type | Role |
|---|---|---|
| Majority classifier | Baseline | Establishes the performance floor |
| Logistic regression | Linear model | Interpretable transaction-level baseline |
| XGBoost | Gradient-boosted trees | Primary transaction-level model |
| Temporal engine | Rolling z-score statistics | Burst/anomaly signal |
| Graph engine | NetworkX graph analytics | Coordinated-abuse signal |
| Reputation engine | Historical aggregation | Entity risk prior |
| Risk fusion | Weighted combination | Unified 0–100 score |

The design keeps component scores separate until fusion, which is what makes the
ablation study (transaction → +temporal → +graph → +reputation) possible.

---

## 2. Intended use

**Intended users.** Fraud analysts (triage), fraud investigators (ring analysis),
and ML/risk engineers (evaluation) — the three roles in `PRD.md` §3.

**Intended use.** Produce explainable risk scores and alerts that a human reviews
before any consequential action. Support investigation of coordinated abuse via
graph exploration. Enable measurement of where transaction-level ML succeeds and
fails relative to graph-based detection.

**Out-of-scope uses.**

- Autonomous blocking, holding, or closing of any account. The system's most
  severe autonomous action is raising a CRITICAL alert and recommending a hold;
  a human decides.
- Any real-money or real-customer decisioning.
- Deployment against real financial data.
- Use as evidence of real-world fraud rates or losses.
- Regulatory/compliance determinations (AML, KYC, sanctions).

---

## 3. The human-in-the-loop boundary

This is a defining property, not a feature. Risk levels map to graded, human-
mediated responses:

| Level | Score band* | Action |
|---|---|---|
| LOW | lower band | allow |
| MEDIUM | mid band | monitor |
| HIGH | upper band | enhanced verification / human review |
| CRITICAL | top band | human review / temporary hold |

*Exact band boundaries are configurable and set from validation analysis, not
asserted here. The model never blocks a customer on its own output. The AI
Copilot (added last) summarises evidence and explicitly must not recommend
blocking or invent facts.

---

## 4. Training data

**Nature.** Entirely synthetic. No real transactions, customers, or PII exist
anywhere in the pipeline. Generated by `simulator/` with a master seed for full
reproducibility. See `DATA_DICTIONARY.md`.

**Composition.** Customers, merchants, accounts, devices, IPs, beneficiaries, and
transactions, with non-trivial normal behaviour (heterogeneous volumes, per-entity
spending profiles, legitimate outliers, limited legitimate device/IP sharing,
daily/weekly/hourly seasonality) and seven parameterized attack families injected
as fraud.

**Prevalence.** Configurable (1/5/10/25%); primary synthetic benchmark
configuration is 5%. This is a benchmark choice, not a real-world rate.

**Splits.** Strict temporal 60/20/20 (train/validation/held-out), with attack
configurations differing across splits to test generalization. Held-out sealed
until Checkpoint 6. See `docs/DATA_SPLIT_PROTOCOL.md`.

**Labels.** Ground truth is generated with the data and quarantined from every
inference path (see `docs/FEATURE_LEAKAGE_POLICY.md`).

---

## 5. Features

Point-in-time behavioural features across transaction, velocity, volume,
behaviour, geography, entity, and temporal-intelligence groups. Every feature for
a transaction at time `T` uses only data with `ts < T`. Full catalogue and
provenance in `docs/FEATURE_REFERENCE.md`.

A deliberate property: no per-transaction feature encodes a relationship between
entities. That representational gap is why coordinated abuse is expected to evade
transaction-level models and is the motivation for the graph layer.

---

## 6. Evaluation

**Metrics.** Primary: PR-AUC, precision, recall, F1. Secondary: ROC-AUC, confusion
matrix, FPR, FNR. Plus Total Error Cost. Accuracy is explicitly not primary.
Definitions in `EVALUATION.md`.

**Evaluation levels.** Transaction-level, entity-level, ring-level, and temporal
detection latency — reported separately so coordinated-abuse performance is not
averaged into individual-anomaly performance.

**Results.** Transaction-level baseline results are frozen historical evidence in
`README.md` and `docs/SUBMISSION_RESULTS.md`. Entity, ring, temporal-latency,
ablation, and reputation results remain **Not yet measured.**

| Level | Metric family | Status |
|---|---|---|
| Transaction | PR-AUC, precision, recall, F1, cost | Frozen Checkpoint 2H evidence; see `docs/SUBMISSION_RESULTS.md` |
| Entity | precision, recall, F1 | Not yet measured. |
| Ring | precision, recall, F1, cluster overlap | Not yet measured. |
| Temporal | detection latency | Not yet measured. |

## 7. Limitations

- **Synthetic data ceiling.** The system can only detect abuse the generator
  produces. The generator's assumptions become the system's apparent strengths and
  its blind spots.
- **Circular validity.** The same project defines the attacks and the detectors.
  Split-varying attack parameters mitigate but do not remove this.
- **Representational blindness of transaction models.** Per-transaction models
  cannot see coordination; this is expected and measured, not fixed by tuning.
- **Synthetic costs.** Absolute cost totals have no external meaning; only relative
  comparisons under identical assumptions are informative.
- **No adversarial adaptation or long-horizon drift.** Simulated attackers do not
  react to detection; tactics do not evolve over time.
- **Graph completeness assumption.** Real identity resolution is far noisier and
  sparser than the clean links the synthetic graph provides.
- **Prototype scale.** Volumes and latency are portfolio-scale.

---

## 8. Ethical and safety considerations

- No real PII, ever, by construction.
- Human review precedes all consequential actions.
- Every alert is explainable; no black-box adverse action.
- The LLM Copilot summarises existing evidence only and cannot decide fraud or
  recommend blocking.
- Evidence must map to a real signal; fabricated evidence is prohibited and guarded
  against in code.

---

## 9. Maintenance and versioning

Model versions are tracked (`model_versions` table) and referenced in experiment
records. Lightweight monitoring covers model version, feature drift, prediction
distribution, latency, and error rate (Checkpoint 6). Every reported metric carries
its split, seed, threshold, cost configuration, and the synthetic-data caveat, per
`docs/EXPERIMENT_PROTOCOL.md`.
